要件3番台設定および危険度高め要件 CloudWatch Alarmテスト手順

目的:
要件3.4から3.7について、検証環境で実施する恒久設定、事前準備、影響確認、配信確認、切り戻し、証跡を整理する。
危険度の高い監視要件について、実業務リソースへ影響する操作を避けながら、CloudWatch Alarmの通知到達、Metric Filterの検知条件、CloudTrailイベントの確認方法を整理する。

対象:
3.4 CloudTrailログ保存先S3のServer Access Logging
3.5 CloudTrailログのカスタマー管理KMSキー暗号化
3.6 カスタマー管理KMSキーの自動ローテーション
3.7 全対象VPCのVPC Flow Logs
4.2 MFAなしコンソールログイン監視
4.3 rootアカウント使用監視
4.5 CloudTrail設定変更監視
4.7 CMK無効化または削除予約監視
4.9 AWS Config変更監視
4.12 Network Gateway変更監視
4.14 VPC変更監視
4.15 AWS Organizations変更監視

準危険要件:
4.4 IAMポリシー変更監視
4.8 S3バケットポリシー変更監視
4.10 Security Group変更監視
4.11 NACL変更監視
4.13 Route Table変更監視

基本方針:
本番または業務利用中リソースに対して、停止、削除、無効化、経路変更、認証方式変更を伴う実イベントテストは行わない。
通知経路の確認は、原則としてCloudWatch Alarmの手動状態変更で行う。
検知条件の確認は、CloudWatch LogsのMetric Filter Pattern Testまたは既存CloudTrailログで行う。
停止、削除予約、無効化、通信経路変更など危険を伴う実イベントテストは、承認済みの検証環境だけで行う。
検証環境でも、業務検証に使用中のリソースではなく、既存処理から分離したテスト専用リソースを使用する。
テスト用変更の戻しまたは削除は、Alarm表示だけで判断せず、通知到達と必要証跡の取得を完了した後に行う。
この基本方針の「テスト専用リソース」は、主に4番台のアラーム発報試験へ適用する。3番台の恒久是正では、承認済みの対象Trail、Source Bucket、CMK、VPCへ正式設定を反映する。

実施環境の定義:
本手順でいう検証環境は、実際のAWSアカウント上に存在する承認済みの開発・検証用アカウントまたは検証用領域を指す。
危険を伴う実イベントテストは検証環境だけを対象とし、本番環境では実施しない。
本番環境では、検証環境のEnd-to-Endテスト証跡、設定値の一致、CloudTrailからCloudWatch Logsへの配信、Metric Filter、Alarm Action、通知先SNS Topicの設定を確認して判定する。
本番環境で危険操作による実イベントテストを求められた場合は、通常の本番リリースとは分け、個別の変更承認、影響確認、専用リソース、切り戻し手順、立会者をそろえた別作業として扱う。本手順の対象外とする。

検証環境で実施する場合の前提:
1. 検証環境が他チームの結合試験、性能試験、運用試験に使用されていない時間帯を選ぶ。
2. アカウント、リージョン、VPC、Trail、KMS Key、SNS Topicなどの対象を変更申請と突合する。
3. 既存業務リソースではなく、未関連付け、未アタッチ、未使用のテスト専用リソースを使用する。
4. A-gate、SCP、Permission Boundary、AWS Config、Security Hub、EventBridge、監視製品による拒否、自動修復、自動起票の有無を確認する。
5. 通知確認者へ、作成イベントと削除イベントの両方でテスト通知が届く可能性を事前連絡する。
6. テスト用リソースの作成、変更、戻し、削除に必要な権限を作業前に確認する。
7. テスト専用リソースを作れない場合は、危険な実イベントを実施せず、方式A、方式B、方式Cの組合せへ切り替える。

テスト専用リソースの粒度:
要件ごとに専用AWSアカウントや専用VPCを新設する必要はない。
IAM Policy、KMS Key、S3 Bucket、Config Ruleは、検証環境内に要件別の未使用リソースを作成する。
Security Group、NACL、Route Tableは、既存の検証VPC内に未関連付けのテスト専用リソースを作成できる。ただし4.10から4.14を連続して確認する場合は、空のテスト専用VPCにまとめる方が誤関連付けを防ぎやすい。
CloudTrailからCloudWatch Logsへの連携有効化など、承認済みの是正作業そのものが監視対象eventNameを発生させる場合は、その実イベントをEnd-to-End確認に使用し、発報だけを目的とする追加変更を行わない。

検証環境でも想定される影響:
1. 共用影響
検証環境も共用環境である。既存リソースを誤って選択すると、他チームの試験、バッチ、疎通確認、運用確認へ影響する。

2. 通知および運用影響
SNS、メール、Teams、A-gate、監視製品、インシデント管理システムへテスト通知が送信される。自動起票、電話連絡、エスカレーション、重複通知が発生する可能性がある。
テスト用リソースの削除や設定の戻しも監視対象eventNameに一致し、追加通知を発生させる場合がある。

3. CloudTrailおよびCloudWatch影響
CloudTrailからCloudWatch Logsへの配信、Metric Filter、Alarm評価には反映遅延がある。Alarm画面にALARMが表示された時点で通知先への到達が完了しているとは限らない。
テスト用Trailを追加すると、ログの重複、S3およびCloudWatch Logsへのログ量増加、少額の料金増加が発生する場合がある。既存Trailの停止、削除、Event Selector変更は行わない。

4. IAM影響
テスト用IAM PolicyをUser、Role、Groupへ誤ってアタッチすると権限が変化する。テスト用PolicyはどのPrincipalにもアタッチしない。

5. KMS影響
業務用KMS Keyを無効化または削除予約すると、暗号化、復号、CloudTrailログ配信、アプリケーション処理が失敗する可能性がある。4.7の発報試験ではテスト専用Keyだけを使用する。
3.5および3.6の恒久是正では、承認済みのCloudTrail用CMKへ暗号化と自動ローテーションを設定する。対象CMKをテスト目的で無効化または削除予約しない。
KMS Keyは即時削除できない。ScheduleKeyDeletionには7日から30日の待機期間があり、CancelKeyDeletion後のKeyはDisabledのままとなるため、継続利用する場合はEnableKeyが必要となる。

6. S3影響
業務BucketのBucket Policyを誤って変更するとアクセス拒否または意図しない公開につながる。4.8の発報試験では空のテスト専用Bucketだけを使用し、Block Public Accessを維持する。
3.4の恒久是正では、承認済みのCloudTrailログ保存先Source BucketとServer Access Log用Target Bucketを使用する。Target Bucket Policyの変更前後差分を確認する。

7. ネットワーク影響
Route Table、Security Group、NACL、Internet Gateway、VPCを既存SubnetやENIへ誤って関連付けると、通信断または意図しない通信許可が発生する。未関連付けのテスト専用リソースだけを使用する。

8. 統制および自動修復影響
A-gate、SCP、AWS Config Rule、Control Tower相当の統制により操作が拒否される、作成直後に修復される、または違反として記録される場合がある。拒否を回避する変更は行わない。

9. 料金、クォータおよび残存リソース
CloudWatch Logs、カスタムメトリクス、Alarm、S3、KMS Key、Config Ruleなどに少額の料金が発生する場合がある。VPC、Internet Gateway、Route Tableなどのクォータも一時的に消費する。
削除漏れ、タグ漏れ、依存関係の残存があると、後続試験やリソース管理へ影響する。

4番台テスト用設定およびリソースの削除開始条件:
次の確認がすべて完了してから、テスト用設定の戻しまたはリソース削除を開始する。
1. CloudTrailで対象eventName、eventTime、userIdentity、対象リソースIDを確認した。
2. CloudWatch Logsの連携先Log Groupで同一イベントを確認した。
3. 対象カスタムメトリクスにデータポイントが生成されたことを確認した。
4. Alarm履歴でOKからALARMへの遷移を確認した。
5. SNS、メール、Teams、A-gateまたは監視基盤で通知到達を確認した。
6. 上記の必要証跡を保存した。

4番台テスト用設定の削除および切り戻し時の注意:
1. AlarmがALARMになったことだけを理由に、ただちにテスト用設定を削除しない。通知先への到達と証跡保存を先に完了する。
2. 通知確認後は、作業計画で定めた順序に従い、テスト目的だけで追加した設定またはリソースを速やかに戻し、または削除する。
3. DeletePolicy、DeleteTrail、DeleteBucketPolicy、DeleteConfigRule、DeleteRouteなど、削除操作自体がMetric Filterに一致する場合は、追加通知を正常なテスト結果として記録する。
4. 削除後も、評価期間と欠損データの扱いによりAlarmが一定時間ALARMのまま残る場合がある。リソース削除はAlarm状態を強制的にOKへ戻す操作ではない。
5. 欠損データがnotBreachingの場合は次回評価後にOKへ戻ることを確認する。手動でOKへ戻す場合は、実データによる評価結果と混同しないよう理由を記録する。
6. KMS Keyは即時削除できない。ScheduleKeyDeletionをCancelKeyDeletionした後、継続利用しない場合は、廃止承認に従って再度削除予約し、削除予定日と確認担当者を管理する。
7. 共用のテストVPCを複数要件で使用する場合は、各要件固有のRuleやRouteだけを都度削除し、VPC本体は全ネットワーク要件の確認完了後に依存リソースとともに削除する。
8. 削除後は、対象一覧、関連付け、アタッチメント、Alarm状態、通知履歴を確認し、テスト用リソースが残っていないことを証跡として保存する。

要件3番台の作業方針:
要件3.4から3.7は、アラーム発報だけを目的とする一時変更ではなく、監査指摘を是正するための設定変更である。
検証環境へ正式に反映したServer Access Logging、CloudTrail SSE-KMS、CMK自動ローテーション、VPC Flow Logsは、テスト完了後も原則として残す。
作業後に削除するのは、発報確認や手順検証だけを目的として作成したテスト専用Bucket、KMS Key、Log Group、IAM Roleなどに限定する。
恒久設定を切り戻す場合は、障害、配信失敗、権限不備などの切り戻し条件に該当し、承認者が切り戻しを判断した場合だけとする。

要件3番台の実施順序:
1. 対象アカウント、対象環境、対象リージョン、対象リソース一覧を確定する。
2. A-gate、SCP、Permission Boundary、既存基盤統制と作業分担を確認する。
3. 変更前設定と既存Policyを証跡保存する。
4. 3.4のServer Access Logging送信先を確定する。
5. 3.5のCloudTrail暗号化用CMKを確定または作成する。
6. 3.6の自動ローテーションを同じCMKで有効化する。
7. 3.5の対象TrailへCMKを設定し、新規CloudTrailログの配信と暗号化を確認する。
8. 3.4のServer Access Loggingを有効化し、送信先への配信を確認する。
9. 3.7の対象VPCごとにVPC Flow Logsを作成し、送信先への配信を確認する。
10. 変更後設定、配信結果、エラーの有無を証跡保存する。

要件3番台の共通事前準備:
1. 変更申請番号、承認者、実施者、確認者、実施日時、切り戻し判断者を確認する。
2. 検証、Prod、OPERのどの環境が対象かを確認する。
3. 対象AWSアカウントIDと対象リージョンを一覧化する。
4. 対象Trail名、Trail ARN、Home Region、S3保存先Bucket、Prefixを確認する。
5. 対象S3 Bucket、対象KMS Key、対象VPCをリソースIDで一覧化する。
6. 既存のログ集約Bucket、KMS Key、CloudWatch Logs Log Group、VPC Flow Logs用IAM Roleを再利用できるか確認する。
7. 新規リソースが必要な場合は、命名規則、タグ、管理部署、費用配賦、保持期間、廃止方法を確定する。
8. パラメータシート、CloudTrail設計書、S3設計書、KMS設計書、VPC構成図、Flow Logs設計書を準備する。
9. 変更前のBucket Policy、KMS Key Policy、Trail設定、Flow Log一覧を保存する。
10. 設定変更後のログ到達確認に必要な待機時間を作業計画へ組み込む。
11. A-gateまたは基盤側が設定主体の場合は、業務側が直接変更せず、設定値と確認観点を依頼票へ記載する。

1. AWS Management Consoleへログインする。

3. CloudTrailコンソールを開く。
4. 左メニューの「証跡」を開き、対象Trailを選択する。
5. Trail名、Home Region、Multi-Region、Organization Trail、S3 Bucket、Prefix、KMS Key、Log file validationを確認する。

8. KMSコンソールで既存のCloudTrail用CMK候補を確認する。
9. VPCコンソールで対象VPC一覧と既存Flow Logを確認する。
10. 変更対象と変更しないリソースを作業記録へ記載する。

3.4 CloudTrailログ保存先S3 Server Access Logging:

目的:
CloudTrailログ保存先のSource Bucketに対するアクセスを、別のS3 Target BucketへServer Access Logとして保存する。

事前確認:
1. Source Bucketが対象Trailのログ保存先と一致することを確認する。
2. 既存のServer Access Logging用Target Bucketがあるか確認する。
3. 既存Target Bucketを使用するか、新規作成するか承認を得る。
4. 承認済みの既存Target Bucketが後続条件を満たす場合、新規Bucket作成は不要とする。
5. Source BucketとTarget Bucketが同一AWSアカウントかつ同一リージョンであることを確認する。
6. Target BucketをSource Bucket自身にしない。
7. Target Bucket自身のServer Access Loggingを無効のままとする。
8. Target BucketでObject Lockおよびデフォルト保持期間が設定されていないことを確認する。
9. Target BucketでRequester Paysが無効であることを確認する。
10. Target Bucketのデフォルト暗号化をSSE-S3とする。S3 Bucket宛てServer Access Log配信ではSSE-KMSを使用しない。
11. Target BucketのObject OwnershipがBucket owner enforcedの場合、ACLではなくBucket Policyでログ配信を許可する。
12. Target Prefix、Log object key format、Lifecycle、保持期間を確認する。
13. 既存Bucket Policyを変更前証跡として保存する。

既存Target Bucketを使用する場合:
1. S3コンソールでTarget Bucketを開く。
2. 「プロパティ」でAWSリージョン、デフォルト暗号化、Object Lock、Requester Paysを確認する。
3. 「アクセス許可」でObject Ownership、Public Access Block、Bucket Policyを確認する。
4. 「管理」でLifecycle Ruleを確認する。
5. 他のSource Bucketも同じTarget Bucketを使用しているか確認する。
6. Target Prefixが他環境または他Bucketと衝突しないことを確認する。

新規Target Bucketを作成する場合:
1. S3コンソールの「汎用バケット」から「バケットを作成」を選択する。
2. 現場命名規則に沿ったBucket名を入力する。
3. Source Bucketと同じAWSリージョンを選択する。
4. Object Ownershipは「ACL無効 Bucket owner enforced」を選択する。
5. Block Public Accessはすべて有効にする。
6. Bucket Versioningはパラメータシートに従う。
7. デフォルト暗号化はSSE-S3を選択する。
8. Object Lockは有効化しない。
9. 承認済みタグを設定して作成する。
10. 「管理」タブで承認済みのLifecycle Ruleを設定する。
11. 「アクセス許可」タブで作成後のBucket Policyを確認する。

Target Bucket Policyの確認項目:
Principalはlogging.s3.amazonaws.comとする。
Actionはs3:PutObjectとする。
Resourceはarn:aws:s3:::<TargetBucket>/<TargetPrefix>*とする。
aws:SourceAccountはSource Bucket所有アカウントIDに限定する。
aws:SourceArnはarn:aws:s3:::<SourceBucket>に限定する。
既存Policy Statementを削除または上書きしない。
S3コンソールからServer Access Loggingを有効化すると、Target Bucket Policyへログ配信許可が自動追加される。保存前後のPolicy差分を確認する。

Server Access Logging有効化手順:
1. S3コンソールでSource Bucketを開く。
2. 「プロパティ」タブを開く。
3. 「サーバーアクセスのログ記録」まで移動する。
4. 変更前状態を証跡保存する。
5. 「編集」を選択する。
6. Server Access Loggingを「有効にする」へ変更する。
7. 送信先は、承認済みのS3汎用Target Bucketを指定する。
8. Target Prefixをパラメータシートどおりに入力する。
9. Log object key formatをパラメータシートどおりに選択する。
10. 保存前にSource Bucket、Target Bucket、Target Prefixを再確認する。
11. 「変更の保存」を選択する。
12. Source Bucketの「サーバーアクセスのログ記録」が有効になったことを確認する。
13. Target Bucket Policyに必要なログ配信許可だけが追加されたことを確認する。

配信確認手順:
1. Source Bucketに対して、承認済みの読み取り操作を1回実施する。S3コンソールでSource Bucketの「オブジェクト」一覧を開いて更新する操作でよい。
2. Target Bucketを開く。
3. Target Prefix配下にログオブジェクトが作成されるまで待機する。
4. ログオブジェクト名、更新時刻、サイズを確認する。
5. 権限がある場合はログを開き、Source Bucketへのリクエストが記録されていることを確認する。
6. 設定直後にログがない場合は失敗と断定しない。Server Access Logの配信には数時間かかる場合がある。
7. 当日中に届かない場合は、配信待ちとして設定値と確認時刻を記録し、後続確認を設定する。

3.4の影響:
Source Bucketへの業務アクセスは変更しないが、Target Bucketへのログオブジェクト書き込みとS3保存量が増える。
Target Bucket Policy変更により、設定を誤るとログ配信が拒否される。
Target BucketをSource Bucket自身にするとログ配信が新たなアクセスログを生成し続けるため、使用しない。
Server Access Logはベストエフォート配信であり、即時性および完全性を前提としない。

3.4の切り戻し:
1. 配信失敗または承認済み切り戻し条件を確認する。
2. Source Bucketの「プロパティ」から「サーバーアクセスのログ記録」を編集する。
3. 「無効にする」を選択して保存する。
4. 無効化後の画面を証跡保存する。
5. Target Bucket PolicyからStatementを削除する前に、他のSource Bucketが使用していないことを確認する。
6. テスト専用Target Bucketを削除する場合は、遅延配信がないことを確認し、ログと証跡の保管判断後に空にして削除する。
7. 恒久是正として設定したTarget BucketおよびServer Access Loggingは、テスト完了を理由に削除しない。

3.4のトラブルシューティング:
ログが届かない場合は、同一アカウント、同一リージョン、Target Prefix、Bucket Policy、SSE-S3、Object Lock、Requester Pays、Source Bucketへのアクセス発生、配信待ち時間を順に確認する。
AccessDeniedの場合は、Bucket Policyのlogging.s3.amazonaws.com、s3:PutObject、aws:SourceAccount、aws:SourceArn、A-gateまたはSCPの明示的拒否を確認する。
保存操作で既存Bucket Policyが意図せず変更される表示が出た場合は保存せず中止する。

3.5 CloudTrailログのカスタマー管理KMSキー暗号化:

目的:
対象Trailが新たに配信するCloudTrailログファイルとダイジェストファイルを、承認済みのカスタマー管理対称KMS KeyでSSE-KMS暗号化する。

事前確認:
1. 既存のCloudTrail用CMKを再利用するか、新規CMKを作成するか確認する。
2. KMS KeyとCloudTrailログ保存先S3 Bucketが同じAWSリージョンであることを確認する。
3. KMS KeyがCustomer managed keyであることを確認する。
4. Key specがSYMMETRIC_DEFAULT、Key usageがEncrypt and decryptであることを確認する。
5. Key originがAWS_KMSであることを確認する。
6. Key stateがEnabledであることを確認する。
7. Trail ARN、Trail所有アカウント、Organization Trail管理アカウントを確認する。
8. CloudTrailログを参照する運用Role、監査Role、ログ集約Roleを確認する。
9. S3 Bucket Keyの有無を確認する。既存S3 BucketでS3 Bucket Keyを使用する場合は、CloudTrailに必要なkms:Decryptも確認する。
10. 現在のTrail設定、KMS Key設定、Key Policyを証跡保存する。

既存CMKを使用する場合:
1. KMSコンソールで「カスタマー管理型のキー」を開く。
2. パラメータシートのAliasまたはKey ARNで検索する。
3. Key type、Key usage、Origin、Key state、Regionを確認する。
4. 「キーポリシー」タブを開く。
5. CloudTrail暗号化、CloudTrailによるKey参照、ログ参照者の復号許可があることを確認する。
6. 既存Statementを変更する必要がある場合は、レビュー済みPolicyと完全一致することを確認する。

新規CMKを作成する場合:
1. KMSコンソールを対象リージョンで開く。
2. 「カスタマー管理型のキー」から「キーの作成」を選択する。
3. Key typeは「対称」を選択する。
4. Key usageは「暗号化および復号化」を選択する。
5. Single-RegionまたはMulti-Regionはパラメータシートに従う。要件がなければ勝手にMulti-Region Keyへ変更しない。
6. 現場命名規則に沿ったAlias、Description、タグを入力する。
7. Key administratorsを承認済みRoleに限定する。
8. Key deletion権限を付与する管理者を承認済みRoleに限定する。
9. Key usersへ、CloudTrailログ参照に必要な承認済みRoleだけを指定する。
10. Keyを作成し、Key ARNとKey IDを証跡保存する。
11. Key Policyをレビュー済みPolicyへ更新する。

CloudTrail用Key Policyの必須確認項目:
1. CloudTrailサービスプリンシパルcloudtrail.amazonaws.comへkms:GenerateDataKey*を許可する。
2. aws:SourceArnを対象Trail ARNへ限定する。
3. kms:EncryptionContext:aws:cloudtrail:arnを対象アカウントのTrail ARNへ限定する。
4. CloudTrailがKeyのプロパティを確認するためのkms:DescribeKeyを許可する。
5. CloudTrailログを読む承認済みRoleへkms:Decryptを許可する。
6. Organization Trailまたはクロスアカウントログ集約の場合は、管理アカウント、メンバーアカウント、ログ参照Roleの設計を確認する。
7. 既存の管理者Statement、Root委任、ログ参照者Statementを削除しない。
8. Principal、Account ID、Region、Trail名にプレースホルダーが残っていないことを確認する。

CloudTrail SSE-KMS有効化手順:
1. CloudTrailコンソールを開く。
2. 対象TrailのHome Regionへ切り替える。
3. 左メニューの「証跡」を開く。
4. 対象Trailを選択する。
5. Trail詳細、S3 Bucket、最新配信状態を変更前証跡として保存する。
6. 「編集」を選択する。
7. 「ログファイルのSSE-KMS暗号化」を有効にする。
8. 「既存」を選択し、承認済みKMS Key AliasまたはKey ARNを指定する。
9. 表示されたKey ARNがパラメータシートと一致することを確認する。
10. S3 Bucket、Prefix、Multi-Region、Log file validation、Event Selectorなど、今回変更しない項目が変更前と同じであることを確認する。
11. 「変更の保存」を選択する。
12. Trail詳細でKMS Key IDまたはKMS Key ARNが設定されたことを確認する。

3.5の配信および暗号化確認:
1. CloudTrailの対象Trailを開く。
2. 「証跡のステータス」でLoggingが有効であることを確認する。
3. Latest delivery errorまたは配信エラーがないことを確認する。
4. 新しい管理イベントが発生し、CloudTrailログがS3へ配信されるまで待機する。
5. S3コンソールでCloudTrailログ保存先BucketとPrefixを開く。
6. 変更後に作成された新規CloudTrailログオブジェクトを選択する。
7. 「プロパティ」でServer-side encryptionがAWS-KMSであることを確認する。
8. KMS Key ARNまたはKey IDが3.5の対象CMKと一致することを確認する。
9. 承認済みログ参照Roleで新規ログを開けることを確認する。
10. CloudTrailイベント履歴でUpdateTrailを確認する。
11. KMS関連イベントでGenerateDataKeyが記録されていることを必要に応じて確認する。

3.5の影響:
Key Policy不備、Key無効化、Key削除予約、Region不一致があるとCloudTrailログをS3へ配信できない可能性がある。
S3読取権限だけではログを読めず、ログ参照者にkms:Decryptが必要となる。
設定変更前にSSE-S3で保存された既存ログは、自動的にSSE-KMSへ再暗号化されない。
設定後の新規ログだけが指定CMKで暗号化される。
KMS Key ARNまたはAliasを参照するアプリケーション変更は不要だが、ログ読取Roleの権限確認が必要となる。
KMS Key保有料金とログ参照時のKMS利用料金が発生する。

3.5の切り戻し:
1. 配信エラー、UpdateTrail失敗、ログ参照不可などの切り戻し条件を確認する。
2. 変更後にSSE-KMSで保存されたログオブジェクトの有無を確認する。
3. CloudTrailの対象Trailを編集し、変更前のKMS設定へ戻す。
4. KMS未設定が変更前である場合は、承認済み手順に従いSSE-KMS設定を解除する。
5. TrailのS3 Bucket、Prefix、Event Selectorなど他の設定が変わっていないことを確認する。
6. Trail statusでログ配信が復旧したことを確認する。
7. Key Policyを変更した場合は、保存済みの変更前Policyへ戻す。ただし新規SSE-KMSログの復号に必要なStatementを削除しない。
8. SSE-KMSで保存されたログが1件でも存在する場合、CMKを無効化または削除予約しない。
9. 恒久是正用CMKは、テスト完了を理由に削除しない。

3.5のトラブルシューティング:
Trail保存時にAccessDeniedが出る場合は、KMS KeyのRegion、Key state、kms:GenerateDataKey*、kms:DescribeKey、aws:SourceArn、Encryption Context、S3 Bucket Key、A-gateまたはSCPを確認する。
Trail statusに配信エラーが出る場合は、KMS Key PolicyとS3 Bucket Policyの両方を確認する。
ログをダウンロードできない場合は、S3読取権限とkms:Decrypt権限を分けて確認する。
既存Key Policyを上書きする必要がある表示が出た場合は保存せず中止する。

3.6 カスタマー管理KMSキーの自動ローテーション:

目的:
3.5でCloudTrailログ暗号化に使用するカスタマー管理対称KMS Keyの自動ローテーションを有効にする。

事前確認:
1. 3.5の対象CMKと同じKey ARNであることを確認する。
2. Customer managed keyであることを確認する。
3. 対称暗号化Keyであることを確認する。
4. Key originがAWS_KMSであることを確認する。
5. Key stateがEnabledであることを確認する。
6. Pending deletionではないことを確認する。
7. 監査要件のローテーション周期が1年であることを確認する。
8. 変更前のAutomatic key rotation、Rotation period、Next rotation dateを証跡保存する。

自動ローテーション有効化手順:
1. KMSコンソールを対象リージョンで開く。
2. 左メニューの「カスタマー管理型のキー」を開く。
3. 対象AliasまたはKey IDを選択する。
4. 「キーローテーション」タブを開く。
5. 対象Key ARNが3.5のCMKと一致することを再確認する。
6. 「自動キーローテーション」の「編集」を選択する。
7. Key rotationを「有効」にする。
8. Rotation periodは監査要件およびパラメータシートに従う。1年要件では365日とする。
9. 「保存」を選択する。
10. Automatic key rotationが有効であることを確認する。
11. Rotation periodが365日であることを確認する。
12. Next rotation dateが表示されていることを確認する。

3.6のテストおよび確認:
自動ローテーション設定が有効であること、Rotation period、Next rotation dateを確認すれば設定試験は成立する。
1年後の実ローテーションを待つ必要はない。
監査要件3.6の確認だけを目的として、オンデマンドローテーションを実行しない。
CloudTrailイベント履歴でEnableKeyRotationを確認する。
自動ローテーション後もKey ID、Key ARN、Alias、Key Policy、アクセス許可は変わらない。

3.6の影響:
自動ローテーションはKey materialを更新するが、既存暗号文の復号はAWS KMSが適切な旧Key materialを選択する。
Key IDおよびKey ARNは変わらないため、CloudTrail側のKMS設定変更は不要となる。
KeyがDisabledまたはPending deletionの場合はローテーションされない。
KMS料金への影響は最新料金表と現場の費用見積で確認する。

3.6の切り戻し:
1. 誤ったKeyまたは誤ったRotation periodへ設定した場合に限り切り戻す。
2. 対象CMKの「キーローテーション」タブを開く。
3. Automatic key rotationを変更前設定へ戻す。
4. 変更後状態を証跡保存する。
5. Rotationを無効化しても、既に生成されたKey materialは削除されない。
6. 恒久是正として有効化した自動ローテーションは、テスト完了を理由に無効化しない。

3.6のトラブルシューティング:
「キーローテーション」タブが表示されない場合は、Key type、Key usage、Origin、Custom key store、Key stateを確認する。
Multi-Region KeyではPrimary Key側の設定か確認する。
保存時にAccessDeniedが出る場合は、kms:EnableKeyRotation、Key Policy、Permission Boundary、A-gate、SCPを確認する。

3.7 全対象VPCのVPC Flow Logs:

目的:
承認済み対象VPCのネットワークインターフェイスを通過するIPトラフィックのメタデータを、CloudWatch LogsまたはS3へ配信する。

対象範囲の事前確認:
1. Prod、OPER、検証の対象VPC一覧をVPC IDで確定する。
2. 削除予定VPC、未使用VPC、別システムVPCを除外する場合は承認根拠を記録する。
3. 既存Flow LogがVPC、Subnet、ENIのどの単位で作成されているか確認する。
4. 要件が「すべてのVPC」であるため、SubnetまたはENI単位のFlow Logだけで全ENIを網羅できるか確認する。
5. 同じVPCへ同等のFlow Logを重複作成しない。
6. 送信先をCloudWatch Logs、S3、Data Firehoseのどれにするか確認する。本手順ではパラメータシートのCloudWatch LogsまたはS3を使用する。
7. Traffic type、Maximum aggregation interval、Log format、保持期間、KMS、タグを確認する。

CloudWatch Logs送信先を使用する場合の事前準備:
1. 既存Log Groupを使用するか、新規作成するか確認する。
2. Log Group名、リージョン、Retention、KMS Key、Log class、タグを確認する。
3. VPC Flow Logs配信用IAM Role ARNを確認する。
4. IAM Roleの信頼ポリシーでvpc-flow-logs.amazonaws.comを許可していることを確認する。
5. IAM Roleにlogs:CreateLogGroup、logs:CreateLogStream、logs:PutLogEvents、logs:DescribeLogGroups、logs:DescribeLogStreamsがあることを確認する。
6. 作業者に対象IAM Roleへのiam:PassRoleがあることを確認する。

CloudWatch Logs配信用IAM Roleを新規作成する場合:
1. IAMコンソールを開く。
2. 左メニューの「ポリシー」から「ポリシーを作成」を選択する。
3. JSONエディタへ、logs:CreateLogGroup、logs:CreateLogStream、logs:PutLogEvents、logs:DescribeLogGroups、logs:DescribeLogStreamsをAllowする承認済みPolicyを入力する。
4. Resource範囲は承認済み設計値に従う。AWS公式例のResourceは*だが、現場設計で対象Log Group ARNへ限定できるActionは限定する。
5. Policy名、Description、タグを現場命名規則どおりに設定し、Policyを作成する。
6. 左メニューの「ロール」から「ロールを作成」を選択する。
7. Trusted entity typeで「カスタム信頼ポリシー」を選択する。
8. Principal Serviceをvpc-flow-logs.amazonaws.com、Actionをsts:AssumeRoleとする。
9. 混乱した使節対策としてaws:SourceAccountを対象アカウントIDへ限定する。
10. aws:SourceArnはarn:aws:ec2:<Region>:<AccountId>:vpc-flow-log/*へ限定する。Flow Log ID確定後に個別ARNへ限定する設計の場合は、作成後に信頼ポリシーを更新する。
11. 手順3から5で作成したPolicyを選択する。
12. Role名、Description、タグを現場命名規則どおりに設定し、Roleを作成する。
13. Role ARN、信頼ポリシー、許可Policyを証跡保存する。
14. 作業者がこのRoleをVPC Flow Logsへ渡せるiam:PassRoleを持つことを確認する。

CloudWatch Logs Log Groupを新規作成する場合:
1. CloudWatchコンソールを対象リージョンで開く。
2. 「ロググループ」を開く。
3. 「ロググループを作成」を選択する。
4. 現場命名規則に沿ったLog Group名を入力する。
5. Retentionをパラメータシートどおりに設定する。
6. KMS暗号化が必要な場合は承認済みKMS Keyを指定する。
7. KMS暗号化を使用する場合は、KMS Key Policyでlogs.<Region>.amazonaws.comへ必要な暗号化操作を許可し、kms:EncryptionContext:aws:logs:arnを対象Log Group ARNへ限定する。
8. Log classとタグをパラメータシートどおりに設定する。
9. 作成後のLog Group ARNを記録する。

S3送信先を使用する場合の事前準備:
1. 既存S3 Bucket ARNとOptional prefixを確認する。
2. Bucketのリージョン、暗号化、Lifecycle、Public Access Block、Bucket Policyを確認する。
3. CloudWatch Logsを送信先とする場合、3.7のためのS3 Bucket作成は不要とする。
4. Flow Log作成者がBucket所有者で、s3:GetBucketPolicyおよびs3:PutBucketPolicyを持つ場合、Flow Log作成時にAWSの配信Policyが自動アタッチされる。
5. この自動アタッチは既存Bucket Policyを上書きする。共有Bucketまたは既存PolicyがあるBucketでは、そのままFlow Logを作成せず、Bucket所有者および基盤担当と対応方式を確定する。
6. 既存Policyを維持する場合は、Bucket所有者または基盤担当がAWSLogDeliveryWriteおよびAWSLogDeliveryAclCheckの必要Statementを既存Policyへマージする。
7. Flow Log作成者がBucketを所有しない、またはPolicy更新権限を持たない場合、必要StatementをBucket所有者が事前追加しなければFlow Log作成は失敗する。
8. aws:SourceAccountおよびaws:SourceArnで配信元を限定する。
9. S3 Bucket ARNのOptional prefixにAWSLogsを直接指定しない。
10. Target Bucketのデフォルト暗号化がSSE-S3の場合、追加のKMS設定は不要となる。
11. Target Bucketのデフォルト暗号化がSSE-KMSの場合、カスタマー管理KMS Key ARNを使用する。Key IDだけを指定した設定ではLogDestination undeliverableとなる可能性がある。
12. SSE-KMSの場合、ログ配信サービスがS3へ書き込めるよう、対象CMKのKey Policyへ承認済みのログ配信許可を追加する。

VPC Flow Log作成手順:
1. VPCコンソールを対象リージョンで開く。
2. 左メニューの「お使いのVPC」を開く。
3. 対象VPC IDを検索する。
4. VPC名、CIDR、環境タグを確認し、対象VPCであることを再確認する。
5. 対象VPCを選択し、「フローログ」タブを開く。
6. 変更前のFlow Log一覧を証跡保存する。
7. 「フローログを作成」を選択する。
8. Nameを現場命名規則に従って入力する。
9. Filterはパラメータシートに従う。監査要件で全通信を対象とする場合は「すべて」を選択する。
10. Maximum aggregation intervalをパラメータシートどおりに選択する。
11. DestinationでCloudWatch LogsまたはS3を選択する。
12. CloudWatch Logsの場合は、送信先Log GroupとサービスアクセスIAM Roleを指定する。
13. S3の場合は、承認済みS3 Bucket ARNとOptional prefixを指定する。
14. Log record formatはパラメータシートどおりに、AWS default formatまたはCustom formatを選択する。
15. 追加メタデータを使用する場合は設計値に従う。
16. 承認済みタグを設定する。
17. 作成前確認画面でVPC ID、Filter、Destination、IAM Role、Log formatを再確認する。
18. 「フローログを作成」を選択する。
19. VPCの「フローログ」タブでFlow Log IDとStatusを確認する。
20. 対象VPCが複数ある場合は、対象一覧と突合しながら1VPCずつ繰り返す。

3.7の配信確認:
1. Flow Log StatusがActiveであることを確認する。
2. CloudWatch Logsの場合は、対象Log Groupを開く。
3. 対象ENIに対応するLog Streamが作成されていることを確認する。
4. Log eventを開き、account-id、interface-id、srcaddr、dstaddr、srcport、dstport、protocol、action、log-statusなどを確認する。
5. S3の場合は、対象BucketとPrefixを開く。
6. AWSLogs配下にVPC Flow Logsのログオブジェクトが作成されていることを確認する。
7. 既存トラフィックがあるVPCでは、CloudWatch Logsへ通常約5分、S3へ通常約10分を目安に待機する。
8. 対象VPCにアクティブなネットワークトラフィックがない場合、ログが表示されなくても直ちに設定失敗と判断しない。
9. 安全な通信確認が承認されている場合だけ、既存の検証用ENIから既存の許可済み接続先へ疎通を1回行う。
10. Flow Log確認だけを目的としてSecurity Group、NACL、Route Tableを変更しない。
11. log-statusがOKであることを確認する。NODATAは対象期間に通信がなかったことを示し、SKIPDATAは一部レコード欠落の可能性を示す。

3.7の影響:
VPC Flow Logsはトラフィック経路外で収集されるため、作成または削除してもネットワークのスループットやレイテンシーには影響しない。
CloudWatch LogsまたはS3へのログ取込量、保存量、検索量が増え、料金が発生する。
IPアドレス、Port、Protocol、Actionなどの通信メタデータが保存されるため、閲覧権限と保管期間を管理する。
IAM Role、Log Group、S3 Bucket Policy、KMS Keyの設定不備により配信失敗となる可能性がある。
Flow Log作成後はDestination、IAM Role、Log formatなどを変更できない。設定誤りの場合はFlow Logを削除して再作成する。

3.7の切り戻し:
1. 配信失敗または誤設定などの切り戻し条件を確認する。
2. VPCの「フローログ」タブで対象Flow Log IDを選択する。
3. 対象VPC ID、Destination、作成日時を再確認する。
4. 「アクション」から「フローログを削除」を選択する。
5. 削除後、対象Flow Log IDが一覧から消えたことを確認する。
6. Flow Logを削除しても、CloudWatch LogsまたはS3に既に配信されたログは削除されない。
7. テスト専用Log Group、IAM Role、S3 Bucketを削除する場合は、他のFlow Logが使用していないことを確認する。
8. 恒久是正として作成したVPC Flow Logは、テスト完了を理由に削除しない。

3.7のトラブルシューティング:
StatusがFailedの場合は、Delivery error、Log Group、IAM Role、Trust policy、iam:PassRole、S3 Bucket Policy、KMS Key、A-gateまたはSCPを確認する。
StatusがActiveでもログがない場合は、対象VPCのトラフィック有無、Log GroupまたはS3 Prefix、リージョン、待機時間を確認する。
CloudWatch Logs配信でAccessDeniedの場合は、vpc-flow-logs.amazonaws.comの信頼、CreateLogStream、PutLogEvents、DescribeLogStreamsを確認する。
S3配信でAccessDeniedの場合は、delivery.logs.amazonaws.com、aws:SourceAccount、aws:SourceArn、Bucket Policyを確認する。
パラメータ誤りが判明した場合は、Flow Logをその場で重複作成せず、既存の誤設定Flow Logを切り戻してから正しい設定で再作成する。

要件3番台の作業後確認:
1. 3.4 Source BucketのServer Access Loggingが有効で、Target BucketとTarget Prefixが設計値と一致することを確認する。
2. 3.4 Target Bucketへアクセスログが配信されたこと、または配信待ち記録があることを確認する。
3. 3.5 TrailのKMS Key ARNが設計値と一致し、Trail statusに配信エラーがないことを確認する。
4. 3.5 変更後の新規CloudTrailログが対象CMKでSSE-KMS暗号化されていることを確認する。
5. 3.5 承認済みログ参照Roleで新規ログを読めることを確認する。
6. 3.6 Automatic key rotationが有効で、Rotation periodが365日であることを確認する。
7. 3.7 全対象VPCにFlow Logが存在し、StatusがActiveであることを確認する。
8. 3.7 Log GroupまたはS3へログが配信されたこと、またはNODATAの理由が記録されていることを確認する。
9. 変更前後のパラメータシート、設計書、作業記録を更新する。
10. A-gateまたは基盤側作業が残る場合は、未完了項目、担当、期限を記録する。

要件3番台の共通中止条件:
対象アカウント、対象リージョン、対象環境が変更申請と一致しない。
対象Trail、Source Bucket、KMS Key、VPCを一意に特定できない。
パラメータシートにTarget Bucket、KMS Key、Flow Logs Destinationなどの必須値がない。
既存Bucket PolicyまたはKey Policyを保存できない。
保存時に既存Policyを意図せず上書きする可能性がある。
必要なIAM権限またはiam:PassRoleがない。
A-gate、SCP、Permission Boundaryによる明示的拒否が発生する。
ログ参照者、保持期間、費用負担、運用担当が未決定である。
切り戻し手順または切り戻し判断者が未確定である。
既存業務リソースへの想定外変更が必要となる。

テスト方式の採用順:
1. 手動ALARM遷移で通知到達を確認する。
2. Metric Filter Pattern Testで検知条件を確認する。
3. 既存CloudTrailログで過去イベントの検知条件を確認する。
4. テスト専用リソースで軽微な実イベントを発生させる。
5. 本番環境または業務リソースでの危険な実イベントは採用しない。例外要求は別作業として承認を取り直す。

方式A: 手動ALARM遷移による通知到達確認
用途:
危険操作を起こさず、CloudWatch AlarmからSNS、メール、Teams、監視基盤へ通知が届くことを確認する。

Webコンソール手順:
1. AWS Management Consoleへログインする。
2. 対象アカウント、対象リージョンを確認する。
3. CloudWatchを開く。
4. 左メニューで「アラーム」を開く。
5. 「すべてのアラーム」を開く。
6. 対象Alarm名を検索する。
7. 対象Alarmを選択する。
8. 画面右上またはActionsメニューから「状態の設定」または「Set state」を選択する。
9. State valueに「ALARM」を選択する。
10. State reasonに「テストリハ通知確認。危険実イベント回避のため手動ALARM遷移」と入力する。
11. 保存する。
12. Alarm状態がALARMへ変化したことを確認する。
13. Alarm履歴を開き、手動状態変更の履歴を確認する。
14. 通知確認者へメール、Teams、監視基盤の通知到達を確認する。
15. 通知到達画面を証跡として保存する。
16. 確認後、同じ手順でState valueを「OK」へ戻す。
17. Alarm履歴でOKへ戻ったことを確認する。

CLI承認時の代替手順:
aws cloudwatch set-alarm-state --alarm-name "<AlarmName>" --state-value ALARM --state-reason "test rehearsal notification check"
aws cloudwatch set-alarm-state --alarm-name "<AlarmName>" --state-value OK --state-reason "test rehearsal restore to OK"

注意:
Alarm Actionは状態遷移時に動作する。既にALARM状態の場合、再通知されない可能性がある。
手動ALARM遷移は通知経路確認であり、Metric Filterの条件一致確認ではない。

方式B: Metric Filter Pattern Testによる検知条件確認
用途:
危険イベントを実際に起こさず、Metric FilterのFilter Patternが想定イベントに一致することを確認する。

Webコンソール手順:
1. CloudWatchを開く。
2. 左メニューで「ログ」から「ロググループ」を開く。
3. CloudTrail連携先Log Groupを開く。
4. 「メトリクスフィルター」タブを開く。
5. 対象Metric Filterを開く。
6. Filter Patternを確認する。
7. Pattern Testまたはテスト欄に対象イベントのサンプルJSONを入力する。
8. テストを実行する。
9. 一致したイベント数またはMatched表示を確認する。
10. Pattern Test結果を証跡として保存する。

注意:
Pattern Testは通知を飛ばさない。
Pattern TestはCloudWatch Alarmの状態遷移確認ではない。
通知到達確認は方式Aと組み合わせる。

擬似ログ投入の扱い:
CloudWatch LogsにはPutLogEventsでログイベントを投入するAPIが存在する。
ただし、CloudTrailが記録した実イベントの代替証跡として、業務用CloudTrail連携先Log Groupへ擬似CloudTrail JSONを投入する運用は採用しない。
擬似ログ投入を使う場合は、テスト専用Log Group、テスト専用Metric Filter、テスト専用Alarmに限定する。
擬似ログ投入は、Metric FilterからAlarmまでの技術動作確認として扱う。
擬似ログ投入は、実CloudTrailイベントが発生したことの証跡として扱わない。

方式C: 既存CloudTrailログによる検知条件確認
用途:
過去に発生済みのイベントを使用し、新しい危険操作を起こさずに確認する。

Webコンソール手順:
1. CloudTrailを開く。
2. 「イベント履歴」を開く。
3. イベント名、リソース名、ユーザー名、期間で検索する。
4. 対象イベントが存在する場合、イベント詳細を開く。
5. eventName、eventSource、userIdentity、requestParameters、errorCodeを確認する。
6. CloudWatch LogsのCloudTrail連携先Log Groupを開く。
7. 対象イベントがLog Groupへ届いているか確認する。
8. Metric Filterの条件に一致する項目を確認する。
9. CloudTrailイベント詳細とCloudWatch Logs側イベントを証跡として保存する。

注意:
CloudTrailイベント履歴は検索範囲や権限で見え方が変わる。
CloudWatch Logs連携が未設定またはA-gate側制御で拒否されている場合、Log Group側で確認できない。

方式D: テスト専用リソースによる実イベント確認
用途:
承認済みの検証環境で、業務影響のないテスト用リソースに限定して実イベントを発生させる。

共通条件:
作業対象が検証環境であること。
テスト用リソース名に「test」「rehearsal」など識別子を付けること。
業務用リソース、既存通信、既存鍵、既存Trail、既存Organizations設定に触れないこと。
作業前に承認者、実施者、確認者、戻し方法を決めること。
通知到達と必要証跡の取得後に、テスト用リソースを削除または元に戻すこと。

実イベント確認の成立条件:
1. 対象Alarmがテスト開始前にOKであることを確認する。
2. 実AWS操作を1回だけ実行する。
3. CloudTrailイベント履歴で対象eventName、eventTime、userIdentity、対象リソースIDを確認する。
4. CloudWatch Logsの連携先Log Groupで同一イベントを確認する。
5. Metric Filterのカスタムメトリクスにデータポイントが作成されたことを確認する。
6. AlarmがALARMへ遷移したことをAlarm履歴で確認する。
7. SNS、メール、Teams、監視基盤の通知到達を確認する。
8. テスト用変更を元に戻し、リソース状態を確認する。
9. 欠損データの扱いがnotBreachingの場合、次の評価後にAlarmがOKへ戻ることを確認する。

待機時の注意:
CloudTrailからCloudWatch Logs、Metric、Alarmまでの反映は同時ではない。
Alarmが直ちにALARMにならなくても、同じ危険操作を繰り返さない。
最初にCloudTrailイベント、次にCloudWatch Logs、次にMetric、最後にAlarmの順で詰まり箇所を確認する。
待機上限は作業計画で定める。Periodが5分の場合の目安は15分とし、超過時は再操作せず中止条件に従う。
同じAlarmがALARM中に追加イベントを発生させても、新しい通知が出ない場合がある。複数eventNameの網羅確認はPattern Testで行い、実イベントは要件ごとに代表1件とする。
AlarmがALARMへ遷移しても、通知先への到達を確認する前にテスト用リソースを削除しない。
通知到達と証跡取得後は、削除操作による追加通知を想定した上で、速やかに切り戻しへ進む。

4.2 MFAなしコンソールログイン監視
危険理由:
MFAなしログインを実際に作る、またはMFAを外す行為は認証統制を弱める。

採用可能なテスト:
方式A 手動ALARM遷移で通知到達を確認する。
方式B ConsoleLogin SuccessかつMFAUsed NoのサンプルJSONでPattern Testを行う。
方式C 既存のConsoleLoginイベントでMFAUsedの値を確認する。

原則禁止:
既存ユーザーのMFA解除。
MFAなしIAMユーザー作成によるログイン。
rootまたは管理者ユーザーでの認証弱体化。

4.3 rootアカウント使用監視
危険理由:
rootログインは権限が極めて強く、テスト目的であっても不要な利用として扱われる。

採用可能なテスト:
方式A 手動ALARM遷移で通知到達を確認する。
方式B userIdentity.type RootのサンプルJSONでPattern Testを行う。
方式C 既存のroot ConsoleLoginまたはroot APIイベントがある場合だけ確認する。

原則禁止:
通知テスト目的のrootログイン。
root認証情報の共有、再設定、操作。

4.5 CloudTrail設定変更監視
危険理由:
Trail停止、削除、Event Selector変更は監査ログ欠落や想定外のログ増減につながる。

採用可能なテスト:
方式A 手動ALARM遷移で通知到達を確認する。
方式B UpdateTrail、StopLogging、DeleteTrail、PutEventSelectorsのサンプルJSONでPattern Testを行う。
方式C 既存のUpdateTrailイベントがある場合だけ確認する。
方式D 承認済み作業としてCloudTrailからCloudWatch Logsへの連携有効化を行う場合、そのUpdateTrailを実イベント確認として利用する。

原則禁止:
StopLoggingの実行。
DeleteTrailの実行。
業務TrailのEvent Selectorをテスト目的で変更すること。

戻し観点:
CloudTrail設定変更を伴った場合、CloudWatch Logs連携先、IAM Role、S3保存先、Multi-region、Log file validation、Event Selectorを作業前設定と突合する。

4.7 CMK無効化または削除予約監視
危険理由:
業務用CMKを無効化すると暗号化、復号、ログ出力、アプリケーション処理に影響する。削除予約は待機期間後に復旧不能となる可能性がある。

採用可能なテスト:
方式A 手動ALARM遷移で通知到達を確認する。
方式B DisableKey、ScheduleKeyDeletionのサンプルJSONでPattern Testを行う。
方式D テスト専用CMKを作成し、DisableKey後すぐEnableKeyする。
方式D 承認済みの場合のみ、テスト専用CMKでScheduleKeyDeletionを行い、通知到達と必要証跡の取得後に速やかにCancelKeyDeletionする。

テスト専用CMK DisableKey手順:
1. KMSを開く。
2. 「カスタマー管理型のキー」を開く。
3. テスト専用CMKを作成する。
4. キー名、キーARN、Key IDを保存する。
5. テスト専用CMKだけを選択する。
6. 「キーアクション」から「無効化」を選択する。
7. 確認画面で対象キーがテスト専用CMKであることを再確認する。
8. 無効化する。
9. CloudTrail Event historyでDisableKeyを確認する。
10. CloudWatch Logsへ届いたDisableKeyイベントを確認する。
11. Metric、Alarm、通知を確認する。
12. 通知到達と必要証跡の取得後、速やかに同じテスト専用CMKを有効化する。
13. 有効化後のKey stateを確認する。

テスト専用CMK ScheduleKeyDeletion手順:
1. KMSを開く。
2. テスト専用CMKだけを選択する。
3. 「キーアクション」から「削除をスケジュール」を選択する。
4. 最短の待機期間を選択する。
5. 対象キーがテスト専用CMKであることを再確認する。
6. 削除予約を実行する。
7. CloudTrail Event historyでScheduleKeyDeletionを確認する。
8. CloudWatch Logsへ届いたScheduleKeyDeletionイベントを確認する。
9. Metric、Alarm、通知を確認する。
10. 通知到達と必要証跡の取得後、速やかに「キーの削除をキャンセル」を実行する。
11. Key stateがPendingDeletionからDisabledへ変わったことを確認する。
12. 継続利用する場合はEnableKeyを実行する。廃止する場合は承認済みのリソース整理方針に従って再度削除予約し、削除予定日を記録する。

原則禁止:
業務用CMKのDisableKey。
業務用CMKのScheduleKeyDeletion。
CloudTrail、S3、EBS、RDS、Secrets Manager、ログ暗号化に使われているCMKでの実イベントテスト。

4.15 AWS Organizations変更監視
危険理由:

採用可能なテスト:
方式A 手動ALARM遷移で通知到達を確認する。
方式B organizations.amazonaws.comのサンプルJSONでPattern Testを行う。
方式C 管理アカウント側の既存Organizationsイベントがある場合だけ確認する。
方式C A-gateまたは既存EventBridgeでOrganizations変更通知が存在する場合、その設定証跡と通知経路証跡で代替確認する。

原則禁止:
テスト目的のアカウント作成。
OU移動。
SCP Attach/Detach。
Organizations設定変更。
管理アカウントでの不要操作。

4.4 IAMポリシー変更監視

作成後、CloudTrail、CloudWatch Logs、Metric、Alarm、通知を確認し、必要証跡の取得後に速やかに削除する。

危険理由:

方式A 手動ALARM遷移で通知到達を確認する。
方式B Route Table変更イベントのサンプルJSONでPattern Testを行う。
方式D 承認済みのテスト用Route Tableを作成し、削除する。

実イベントを行う場合:

既存Routeを変更しない。

作成後、CloudTrail、CloudWatch Logs、Metric、Alarm、通知を確認し、必要証跡の取得後に速やかに削除する。

実AWS環境で実イベントを発生させる場合の詳細手順:

共通事前確認:
1. 変更申請番号、承認者、作業対象アカウント、リージョン、実施時間帯を確認する。
2. A-gate、SCP、Permission Boundary、IAM Policyによる明示的拒否の有無を確認する。
3. CloudTrailがManagement EventのWriteを記録していることを確認する。
4. CloudTrailから対象CloudWatch Logs Log Groupへの配信が正常であることを確認する。
5. 対象Metric Filter、Metric Namespace、Metric Name、Alarm名、SNS Topicを変更パラメータ一覧と突合する。
6. AlarmのActions enabledが有効、開始状態がOK、欠損データの扱いがnotBreachingであることを確認する。
7. 通知確認者へ、テスト通知が複数回届く可能性とテスト用リソース名を連絡する。
8. テスト用リソースの作成権限、削除権限、タグ付与権限を確認する。
9. 各操作後にCloudTrailイベントを確認できるまで次の危険操作へ進まない。
10. 実イベント1件の成功で、そのFilter Patternに含まれる全eventNameを実操作したことにはしない。残りのOR条件はPattern Testで確認する。
11. IAMなどのグローバルサービスイベントはus-east-1へ記録される場合がある。イベント履歴で見つからない場合はus-east-1を確認し、対象TrailでGlobal service eventsが有効であることを確認する。
12. Metric Filter作成前に到着済みの過去ログからは新しいMetric datapointが生成されないため、実イベントはMetric FilterとAlarmの作成後に実施する。

テスト用リソースの共通命名例:
Purposeタグ: alarm-test
ChangeIdタグ: <変更申請番号>
DeleteAfterタグ: <YYYY-MM-DD>
IAM Policy: <システム略称>-alarm-test-policy-<YYYYMMDD>
S3 Bucket: <システム略称>-alarm-test-<AccountId>-<YYYYMMDD>
Trail: <システム略称>-alarm-test-trail-<YYYYMMDD>
Config Rule: <システム略称>-alarm-test-rule-<YYYYMMDD>
VPC: <システム略称>-alarm-test-vpc-<YYYYMMDD>
Subnet: <システム略称>-alarm-test-subnet-<YYYYMMDD>
Internet Gateway: <システム略称>-alarm-test-igw-<YYYYMMDD>
Route Table: <システム略称>-alarm-test-rtb-<YYYYMMDD>
Security Group: <システム略称>-alarm-test-sg-<YYYYMMDD>
Network ACL: <システム略称>-alarm-test-nacl-<YYYYMMDD>

4.2 MFAなしコンソールログイン監視の実イベント:
対象の業務アカウントでは実施しない。
WinAuth、SAML、IAM Identity Center、A-gateなどの認証経路では、AWSへ到達する前に認証失敗となり、想定するConsoleLoginイベントが対象Trailへ記録されない場合がある。
実イベントが必須の場合は、認証統制担当が用意した専用サンドボックスアカウントと無権限の一時テストIDだけを使用する。
既存ユーザーからMFAを外す方法、業務アカウントにMFAなしIAMユーザーを新規作成する方法は採用しない。
実施可否、ログが記録されるアカウント、リージョン、Trail、認証方式を先に認証統制担当へ確認する。

4.3 rootアカウント使用監視の実イベント:
本番、検証、サンドボックスを問わず、通知テスト目的のrootログインまたはroot API操作は採用しない。
方式Aの手動ALARM遷移、方式BのPattern Test、方式Cの既存イベントで確認する。
root実イベントを要求された場合は、セキュリティ責任者の書面承認とroot利用手順を別途必要とし、本手順の対象外とする。

4.4 IAMポリシー変更監視の実イベント:
目的:
業務User、Role、Groupへ一切アタッチしないカスタマー管理ポリシーを作成し、CreatePolicyを発生させる。

手順:
1. IAMコンソールを開く。
2. 左メニューで「ポリシー」を開く。
3. 「ポリシーを作成」を選択する。
4. JSONエディタを選択する。
5. 次のテスト用Policyを入力する。Resourceのバケット名は、実在しないことを確認したテスト名へ置き換える。
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "NoEffectivePermissionForAlarmTest",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::<存在しないテスト用バケット名>/*"
    }
  ]
}
6. Policy名に共通命名例のIAM Policy名を入力し、Purpose、ChangeId、DeleteAfterタグを付ける。
7. 「ポリシーの作成」を選択する。User、Role、Groupへはアタッチしない。
8. CloudTrailイベント履歴でEvent nameをCreatePolicyとして検索し、作成したPolicy ARNを確認する。
9. CloudWatch Logs、Metric、Alarm、通知の順で確認する。
10. IAMのPolicy詳細で「アタッチされたエンティティ」が0であることを再確認する。
11. Policyを削除する。削除時のDeletePolicyも監視対象であるため、テスト通知として記録する。
12. IAM Policy一覧に残っていないことを確認する。

中止条件:
既存Policyと同名である。
PolicyがUser、Role、Groupへアタッチされている。
Permission BoundaryまたはA-gate管理Policyを変更する必要がある。

4.5 CloudTrail設定変更監視の実イベント:
推奨方法:
承認済みのCloudTrail設定変更が作業計画に含まれている場合、そのUpdateTrailを代表実イベントとして使用する。
CloudWatch Logs連携有効化、KMS CMK設定、ログファイル検証設定など、是正作業そのものから発生したUpdateTrailを利用し、テストだけを目的とした追加変更は行わない。

手順:
1. CloudTrailコンソールで「証跡」を開き、対象Trailを選択する。
2. S3 Bucket、Prefix、KMS Key、Log file validation、CloudWatch Logs Log Group、IAM Role、Management Event、Data Eventを変更前証跡として保存する。
3. 承認済み作業手順書に従い、対象項目だけを変更して保存する。
4. CloudTrailイベント履歴でEvent nameをUpdateTrailとして検索する。
5. requestParametersを開き、承認した変更項目と一致することを確認する。
6. CloudWatch Logs、Metric、Alarm、通知の順で確認する。
7. 恒久設定変更の場合は元に戻さず、変更後パラメータとTrail statusを確認する。
8. テスト一時変更の場合だけ、承認済み切り戻し手順で変更前設定へ戻す。

代替方法:
承認済みの検証アカウントで、テスト専用S3 Bucketとテスト専用Trailを作成する。
1. S3でテスト専用Bucketを作成し、Block Public Accessをすべて有効にする。
2. CloudTrailの「証跡」から「証跡の作成」を選択する。
3. Trail名に共通命名例のTrail名を入力し、作成したテスト専用S3 Bucketを指定する。
4. 組織の証跡、Insights、Data Event、CloudWatch Logs連携は無効のままとする。
5. 管理イベントはReadとWriteを対象として作成する。
6. CreateTrailをCloudTrailイベント履歴で確認し、Alarmと通知を確認する。
7. 確認後、テスト専用Trailを削除する。DeleteTrailもテスト通知として記録する。
8. S3 Bucket内のテストログを削除し、Bucketを削除する。

中止条件:
対象がOrganization Trailである。
Security Lake、A-gate、ログ集約アカウントなどの中央統制と競合する。
テストTrail追加によりリージョン上限、二重記録、想定外課金が生じる。

4.7 CMK無効化または削除予約監視の実イベント:
前項の「テスト専用CMK DisableKey手順」と「テスト専用CMK ScheduleKeyDeletion手順」を使用する。
追加確認:
1. Key typeがCustomer managed key、Key usageがEncrypt and decrypt、Key specがSYMMETRIC_DEFAULTであることを確認する。
2. Alias、Description、Purpose、ChangeId、DeleteAfterからテスト専用キーであることを確認する。
3. CloudTrail、S3、EBS、RDS、Secrets Manager、CloudWatch LogsなどのAWSリソースから参照されていないことを確認する。
4. DisableKeyによるAlarm通知到達と必要証跡の取得後は、速やかにEnableKeyを実行する。
5. ScheduleKeyDeletionによるAlarm通知到達と必要証跡の取得後は、速やかにCancelKeyDeletionを実行する。
6. CancelKeyDeletion後のキーはDisabledになるため、必要な場合はEnableKeyを実行する。
7. テスト終了後のキーを削除する場合は、検証用リソース廃止方針に従って改めてScheduleKeyDeletionを行い、削除予定日を管理台帳へ記録する。

4.8 S3バケットポリシー変更監視の実イベント:
目的:
空のテスト専用Bucketへ安全側のDeny Policyを追加し、PutBucketPolicyを発生させる。

手順:
1. S3コンソールで対象リージョンを確認する。
2. 共通命名例のS3 Bucket名で汎用Bucketを作成する。
3. Object OwnershipはBucket owner enforced、Block Public Accessは4項目すべて有効、Versioningは無効、Default encryptionは既定値とする。
4. Bucketが空であり、CloudTrail、Config、ログ保存先などに使用されていないことを確認する。
5. 「アクセス許可」タブの「バケットポリシー」で「編集」を選択する。
6. 次のPolicyを入力する。2か所のBucket名をテスト専用Bucket名へ置き換える。
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyInsecureTransportForAlarmTest",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::<テスト専用Bucket名>",
        "arn:aws:s3:::<テスト専用Bucket名>/*"
      ],
      "Condition": {
        "Bool": {
          "aws:SecureTransport": "false"
        }
      }
    }
  ]
}
7. 変更を保存する。Public Allowが含まれていないことをPolicy内容とBlock Public Accessで再確認する。
8. CloudTrailイベント履歴でPutBucketPolicyを検索し、requestParameters.bucketNameがテスト専用Bucketであることを確認する。
9. CloudWatch Logs、Metric、Alarm、通知の順で確認する。
10. 「バケットポリシー」で「削除」を選択し、DeleteBucketPolicyを発生させる。
11. Bucket Policyが「なし」であることを確認する。
12. 空のテスト専用Bucketを削除する。

中止条件:
Bucket名が業務Bucket、CloudTrailログBucket、ログ集約Bucketと似ており誤認の可能性がある。
Policy StatusがPublicとなる。
VPC Endpoint Policy、A-gate、Config Ruleによる統制違反が表示される。

4.9 AWS Config変更監視の実イベント:
目的:
既存RecorderやDelivery Channelを変更せず、テスト専用Config RuleのPutConfigRuleを発生させる。

前提:
対象リージョンでAWS Config Recorderが既に稼働していること。
Config Ruleの追加がA-gateまたはOrganizationsで中央管理されていないこと。
テスト用S3 Bucketなど、評価対象に限定できるテストリソースが存在すること。

手順:
1. AWS Configコンソールを開き、対象リージョンを確認する。
2. 「設定」でRecorderとDelivery Channelが稼働中であることを確認する。停止、再作成、変更は行わない。
3. 左メニューで「ルール」を開き、「ルールを追加」を選択する。
4. AWS Managed Ruleからrequired-tagsを選択する。
5. Rule名に共通命名例のConfig Rule名を入力する。
6. Scopeは「特定のリソース」を選択し、Resource typeにAWS::S3::Bucket、Resource IDにテスト専用Bucket名を指定する。
7. Parametersはtag1KeyをPurpose、tag1Valueをalarm-testとする。
8. 設定内容を確認し、Ruleを追加する。
9. CloudTrailイベント履歴でPutConfigRuleを検索し、configRuleNameがテスト専用Rule名であることを確認する。
10. CloudWatch Logs、Metric、Alarm、通知の順で確認する。
11. テスト専用Ruleだけを削除し、DeleteConfigRuleを確認する。
12. Recorder、Delivery Channel、既存Ruleに変更がないことを確認する。

中止条件:
AWS Configが未設定または停止中である。
Recorderを有効化しなければRuleを追加できない。
Organization Config RuleまたはConformance Packで管理されている。
テスト専用リソースだけにScopeを限定できない。

4.10から4.14 ネットワーク系実イベント用の隔離テスト基盤:
目的:
既存VPC、業務Subnet、既存通信経路に触れず、空のテスト専用VPC内だけでイベントを発生させる。

テスト値例:
VPC IPv4 CIDR: <承認済みで既存ネットワークと重複しない/28 CIDR>
参考値: 10.254.255.0/28
Subnet IPv4 CIDR: VPCと同じ/28を使用する場合は、そのVPC内に他Subnetを作成しない。
Route destination: 198.51.100.0/24
Security Group source: 192.0.2.0/24
Security Group protocol/port: TCP 65535
NACL source: 192.0.2.0/24
NACL rule: Inbound、Rule number 200、TCP 65535、Allow

注意:
192.0.2.0/24と198.51.100.0/24はドキュメント用アドレスである。
それでも現場のアドレス管理ルールを優先し、承認済みの値へ置き換える。
テストVPCにはEC2、ENI、Load Balancer、NAT Gateway、VPC Endpoint、Transit Gateway Attachment、VPC Peeringを作成しない。

4.14 VPC変更監視の代表実イベント:
1. VPCコンソールを開く。
2. 「VPC」から「VPCを作成」を選択する。
3. 「VPCのみ」を選択する。
4. Name tagに共通命名例のVPC名を入力する。
5. IPv4 CIDR manual inputを選択し、承認済み/28 CIDRを入力する。
6. IPv6 CIDRなし、Tenancy defaultを選択する。
7. Purpose、ChangeId、DeleteAfterタグを付け、VPCを作成する。
8. 作成したVPC IDを記録する。
9. CloudTrailイベント履歴でCreateVpcを検索し、VPC IDを確認する。
10. CloudWatch Logs、Metric、4.14 Alarm、通知の順で確認する。
11. VPC削除は4.10から4.13のテストと後片付けがすべて完了した最後に行う。

4.12 Network Gateway変更監視の代表実イベント:
1. VPCコンソールの「インターネットゲートウェイ」を開く。
2. 「インターネットゲートウェイの作成」を選択する。
3. Name tagに共通命名例のInternet Gateway名を入力し、タグを付けて作成する。
4. 作成したInternet Gatewayだけを選択し、「アクション」から「VPCにアタッチ」を選択する。
5. 前項で作成したテスト専用VPCを選択してアタッチする。
6. 業務VPCへアタッチされていないことをInternet Gateway詳細のVPC IDで確認する。
7. CloudTrailイベント履歴でCreateInternetGatewayまたはAttachInternetGatewayを検索する。
8. CloudWatch Logs、Metric、4.12 Alarm、通知の順で確認する。
9. Customer Gateway系イベントは実イベントを起こさず、Pattern Testで確認する。
10. Internet Gatewayは4.13 Route Tableテストが完了するまでアタッチ状態を維持する。

4.13 Route Table変更監視の代表実イベント:
目的:
テスト専用VPC内の未使用Route Tableにテスト用Routeを追加し、CreateRouteを検知させる。

準備:
1. VPCコンソールの「サブネット」を開く。
2. 「サブネットを作成」を選択し、テスト専用VPC、任意のAvailability Zone、承認済みSubnet CIDRを指定する。
3. Name tagに共通命名例のSubnet名を入力する。
4. Subnet作成後、EC2やENIが存在しないことを確認する。
5. 「ルートテーブル」を開き、「ルートテーブルを作成」を選択する。
6. Nameに共通命名例のRoute Table名、VPCにテスト専用VPCを指定して作成する。
7. CreateRouteTableが4.13 Alarmを先にALARMへ遷移させた場合は、その通知を記録する。CreateRouteを個別確認する場合はAlarmがOKへ戻るまで待つ。

CreateRouteテスト:
1. 作成したテスト専用Route Tableを選択する。
2. 「ルート」タブで「ルートを編集」を選択する。
3. 「ルートを追加」を選択する。
4. Destinationに198.51.100.0/24を入力する。
5. TargetでInternet Gatewayを選択し、テスト専用Internet Gateway IDを選択する。
6. 保存前にRoute Table ID、VPC ID、Destination、Targetがすべてテスト値であることを確認する。
7. 「変更を保存」を選択する。
8. Route Table詳細で198.51.100.0/24のStateがactiveであることを確認する。
9. CloudTrailイベント履歴でCreateRouteを検索する。
10. requestParameters.routeTableId、destinationCidrBlock、gatewayIdがテスト値と一致することを確認する。
11. CloudWatch Logsで同じCreateRouteイベントを確認する。
12. Metricにデータポイントが作成されたことを確認する。
13. 4.13 AlarmがALARMへ遷移したことをAlarm履歴で確認する。
14. SNS、メール、Teams、監視基盤の通知を確認する。

任意のAssociationイベント確認:
1. テスト専用Route Tableの「サブネットの関連付け」タブを開く。
2. 「サブネットの関連付けを編集」を選択する。
3. テスト専用Subnetだけを選択して保存する。
4. AssociateRouteTableをCloudTrailで確認する。
5. 確認後、テスト専用Subnetの明示的関連付けを解除し、DisassociateRouteTableを確認する。
6. テスト専用SubnetがテストVPCのMain Route Tableへ戻ったことを確認する。

Route Table切り戻し:
1. テスト専用Route Tableの「ルート」タブで「ルートを編集」を選択する。
2. 198.51.100.0/24のテスト用Routeだけを削除し、変更を保存する。
3. Local Routeだけになったことを確認する。
4. 明示的なSubnet associationが0であることを確認する。
5. テスト専用Route Tableを削除する。
6. DeleteRouteとDeleteRouteTableも監視対象であるため、発生した通知をテスト通知として記録する。

絶対に行わない操作:
既存Route Tableへの0.0.0.0/0追加。
既存RouteのReplaceRoute。
業務SubnetへのテストRoute Table関連付け。
Direct Connect、Transit Gateway、NAT Gateway、VPC Endpoint、VPNをTargetにしたテストRoute追加。

4.10 Security Group変更監視の代表実イベント:
1. VPCコンソールの「セキュリティグループ」を開く。
2. 「セキュリティグループを作成」を選択する。
3. NameとDescriptionに共通命名例のSecurity Group名、VPCにテスト専用VPCを指定する。
4. Inbound ruleなしで作成する。
5. 作成したSecurity GroupがEC2、ENI、Load Balancerへ関連付いていないことを確認する。
6. 「インバウンドルールを編集」を選択し、Custom TCP、Port 65535、Source 192.0.2.0/24を追加する。
7. 保存し、AuthorizeSecurityGroupIngressをCloudTrailで確認する。
8. CloudWatch Logs、Metric、4.10 Alarm、通知の順で確認する。
9. 追加したInbound ruleだけを削除し、RevokeSecurityGroupIngressを確認する。
10. 関連リソースが0であることを再確認し、テスト専用Security Groupを削除する。

4.11 NACL変更監視の代表実イベント:
1. VPCコンソールの「ネットワークACL」を開く。
2. 「ネットワークACLを作成」を選択する。
3. Nameに共通命名例のNetwork ACL名、VPCにテスト専用VPCを指定して作成する。
4. 「サブネットの関連付け」が0であることを確認する。
5. 「インバウンドルール」から「インバウンドルールを編集」を選択する。
6. Rule number 200、Type Custom TCP、Protocol TCP、Port 65535、Source 192.0.2.0/24、Allowを追加する。
7. 保存し、CreateNetworkAclEntryをCloudTrailで確認する。
8. CloudWatch Logs、Metric、4.11 Alarm、通知の順で確認する。
9. Rule number 200だけを削除し、DeleteNetworkAclEntryを確認する。
10. Subnet associationが0であることを再確認し、テスト専用Network ACLを削除する。

ネットワーク系テスト基盤の削除順序:
1. Security GroupのテストRuleを削除し、Security Groupを削除する。
2. Network ACLのテストEntryを削除し、Network ACLを削除する。
3. Route TableのテストRouteを削除する。
4. テストSubnetとのRoute Table associationを解除する。
5. テスト専用Route Tableを削除する。
6. テスト専用Subnetを削除する。
7. テスト専用Internet GatewayをテストVPCからデタッチする。
8. テスト専用Internet Gatewayを削除する。
9. テスト専用VPCの依存リソースが、Main Route Table、Default NACL、Default Security Groupだけであることを確認する。
10. テスト専用VPCを削除する。
11. VPC、Subnet、Internet Gateway、Route Table、Security Group、Network ACLの各一覧でテスト用リソースが残っていないことを確認する。
12. 削除操作により発生したAlarm通知を異常通知と誤認しないよう、変更申請番号と削除時刻を通知確認者へ連絡する。

擬似ログ投入の技術的根拠:
CloudWatch LogsのPutLogEvents APIには、指定したLog Streamへログイベントをアップロードできる旨が記載されている。
https://docs.aws.amazon.com/ja_jp/AmazonCloudWatchLogs/latest/APIReference/API_PutLogEvents.html

ただし、PutLogEventsはCloudWatch Logsへログイベントを投入するAPIであり、CloudTrailが実際にAWS APIイベントを記録したことの証明ではない。
本手順では、PutLogEventsを本番CloudTrail連携先Log Groupへの擬似CloudTrailイベント投入手段として採用しない。
