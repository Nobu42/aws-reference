# 要件A3/A4 必要作業・他部署連携整理

作成日: 2026-07-15

この資料は、要件A3/A4について、手順書作成前に必要な作業、確認事項、他部署連携、成果物を整理するための作業整理メモである。

正式資料では、A3/A4は以下の指摘として扱う。

| 要件 | 指摘内容 | 対応の考え方 |
| :--- | :--- | :--- |
| A3 | セキュリティアラートに関するモニタリング運用手順書がない | GuardDuty等のアラート確認、異常判定、エスカレーション、対応記録、証跡保存の運用手順を作成する |
| A4 | GuardDutyで検知されたイベント調査に関する証跡が提出されていない | A3の運用手順に沿って調査・判断・記録できる証跡様式を作成し、サンプルまたは既存証跡で説明できる状態にする |

A3は「手順書」、A4は「手順に沿って運用した証跡」として整理する。  
そのため、A4はA3と別々に大きな設定変更を行うものではなく、A3の手順、記録様式、運用試験、証跡サンプルの中で対応する。

## 1. 作業の位置づけ

A3/A4はAWSリソースの設定変更よりも、運用設計と証跡整備が中心である。

主な作業は以下。

1. 既存資料の確認
2. GuardDuty、Security Hub、EventBridge、SNS、Teams/メール通知の現状確認
3. 既存運用、月次確認、障害・インシデント対応フローの確認
4. 他部署へのヒアリング
5. 異常判定基準の整理
6. 一次対応、エスカレーション、業務影響確認先の整理
7. 運用証跡テンプレートの作成
8. 手順書作成
9. 机上確認または運用試験
10. レビュー、承認、提出用証跡整理

## 2. A3で必要な作業

| 区分 | 作業 | 内容 | 主な確認先 |
| :--- | :--- | :--- | :--- |
| 現状整理 | 既存手順書確認 | セキュリティアラート対応手順、障害対応手順、インシデント対応手順、月次確認手順が存在するか確認する | リーダー、運用チーム |
| 現状整理 | 既存監視設定確認 | GuardDuty、Security Hub、CloudWatch Alarm、EventBridge Rule、SNS、Teams/メール通知の有無を確認する | インフラチーム、監視運用担当 |
| 現状整理 | 対象範囲確認 | 対象アカウント、対象リージョン、GuardDuty管理アカウント、メンバーアカウント、対象環境を確認する | インフラチーム、PM |
| 設計 | アラート受付経路整理 | GuardDuty Findingや通知を誰がどの経路で受けるか整理する | 運用チーム、監視運用担当 |
| 設計 | 異常判定基準整理 | Severity、Finding Type、対象リソース、発生回数、既知作業、誤検知、対応不要の判定基準を整理する | セキュリティ担当部署、インフラチーム |
| 設計 | エスカレーション設計 | High以上、業務影響あり、不審なIAM操作、外部通信疑いなどの場合の連絡先と判断者を整理する | セキュリティ担当部署、PM、運用チーム |
| 設計 | 業務影響確認先整理 | EC2、S3、IAM、RDS、ネットワークなど、対象リソースごとに確認先を整理する | アプリ/業務チーム、インフラチーム |
| 手順作成 | 一次確認手順作成 | GuardDuty Finding確認、対象リソース確認、CloudTrail確認、CloudWatch Logs確認、変更管理突合の流れを作成する | インフラチーム、運用チーム |
| 手順作成 | 対応手順作成 | 要対応、対応不要、誤検知、継続調査、エスカレーション、完了判断の流れを作成する | セキュリティ担当部署、運用チーム |
| 手順作成 | 証跡保存手順作成 | スクリーンショット、対応記録、通知メール/Teams、ログ確認結果、判断根拠の保存方法を作成する | 運用チーム、PM |
| 試験 | 机上確認 | Sample Findingまたは既存Findingを使い、手順に沿って判断と記録ができるか確認する | リーダー、運用チーム |
| レビュー | 手順レビュー | 手順書、判定基準、連絡先、証跡様式をレビューに出す | リーダー、セキュリティ担当部署、PM |

## 3. A4で必要な作業

A4は「GuardDutyイベント調査証跡が出ていない」ことへの対応である。  
必要な作業は、A3で作る手順に沿って証跡を残せる状態を作ることである。

| 区分 | 作業 | 内容 | 主な確認先 |
| :--- | :--- | :--- | :--- |
| 現状整理 | 既存証跡確認 | 月次確認記録、GuardDuty確認記録、通知履歴、インシデント記録があるか確認する | 運用チーム、セキュリティ担当部署 |
| 現状整理 | 証跡不足の確認 | どの証跡が不足しているか、監査上何を提出できなかったか確認する | リーダー、PM |
| 設計 | 記録項目整理 | 受付日時、Finding ID、Severity、対象アカウント、対象リソース、判断、対応者、証跡保存先などを定義する | 運用チーム、セキュリティ担当部署 |
| 設計 | 保存先整理 | 記録ファイル、スクリーンショット、通知メール、Teamsログ、調査結果をどこへ保存するか整理する | 運用チーム、PM |
| 設計 | 証跡粒度整理 | 全Findingを記録するか、High以上のみ詳細記録するか、月次集計と個別記録を分けるか確認する | セキュリティ担当部署、運用チーム |
| 作成 | 証跡テンプレート作成 | 日次/随時確認記録、個別アラート対応記録、月次確認記録の様式を作成する | 運用チーム |
| 試験 | サンプル記録作成 | Sample Findingまたは既存Findingをもとに、記録様式へサンプル入力する | リーダー、運用チーム |
| レビュー | 証跡レビュー | 監査説明に使える粒度か、運用で継続可能か確認する | PM、セキュリティ担当部署 |

## 4. 他部署連携が必要な理由

A3/A4はGuardDutyの画面を確認するだけでは完了しない。  
アラート発生後に、誰が、何を見て、誰へ確認し、どの基準で判断し、どの証跡を残すかを決める必要があるため、複数部署との連携が必要になる。

| 連携先 | 確認すること | 理由 |
| :--- | :--- | :--- |
| インフラチーム | GuardDuty、Security Hub、EventBridge、SNS、Teams/メール通知、既存監視基盤の設定 | AWS側の現状と通知経路を確認するため |
| 運用チーム | アラート受信後の一次対応者、対応時間帯、月次確認、対応記録、保存先 | 実際に手順を回す担当を確認するため |
| セキュリティ担当部署 | Severity判断、誤検知判断、対応不要判断、Archive基準、エスカレーション基準 | 異常判定を個人判断にしないため |
| アプリ/業務チーム | Finding対象リソースが業務上正当か、業務影響があるか | 業務影響や正当な通信を確認するため |
| PM/リーダー | A3/A4の対応方針、レビュー先、承認者、提出物、銀行側説明 | 成果物の合意と提出責任を明確にするため |
| 監視基盤/SOC相当 | 既存SIEM、監視ツール、チケット起票、自動通知、自動対応の有無 | AWS側で新規通知を作る前に重複を確認するため |

## 5. 確認すべき資料

| 資料 | 確認する内容 |
| :--- | :--- |
| セキュリティ設計書 | GuardDuty、Security Hub、通知、監視運用の設計方針 |
| 運用設計書 | アラート受付、一次対応、エスカレーション、夜間休日対応 |
| 監視設計書 | 監視対象、通知先、通知条件、監視基盤との連携 |
| パラメータシート | GuardDuty、EventBridge、SNS、CloudWatch Alarm、Security Hubの設定値 |
| 連絡体制表 | 一次対応者、二次対応者、判断者、報告先 |
| インシデント対応手順 | セキュリティ事象発生時の対応フロー |
| 月次確認資料 | 既存のGuardDuty確認、報告、証跡として流用できるか |
| 変更管理手順 | 正当な変更と不審な変更を切り分けるため |
| 既存通知一覧 | メール、Teams、SNS、EventBridge、監視基盤の通知経路 |
| 証跡保管ルール | 証跡の保存先、保存期間、命名規則 |

## 6. ヒアリング項目

### 6.1 PM/リーダー向け

| 確認事項 | 理由 |
| :--- | :--- |
| A3/A4はGuardDuty中心で整理する認識でよいか | 手順書の対象範囲を確定するため |
| CloudWatch AlarmやEventBridge通知もA3/A4の対象に含めるか | セキュリティアラート全体の手順にするか判断するため |
| A4はA3手順の証跡テンプレートで対応済みと整理してよいか | A3/A4の成果物を分けすぎないため |
| 銀行側レビューに出す成果物はどこまでか | 手順書、証跡テンプレート、サンプル記録の要否を決めるため |
| 本番環境でSample Findingや通知テストを行えるか | 運用試験の方法を決めるため |

### 6.2 インフラチーム向け

| 確認事項 | 理由 |
| :--- | :--- |
| GuardDutyはどのアカウント、リージョンで有効か | 対象範囲を確定するため |
| GuardDuty管理アカウントとメンバーアカウントの構成はどうなっているか | どのアカウントでFindingを見るか判断するため |
| GuardDutyの通知はEventBridge、SNS、Teams、メール、監視基盤へ連携されているか | 通知経路を手順書へ反映するため |
| Security HubへGuardDuty Findingを集約しているか | Finding確認先をGuardDutyに限定してよいか判断するため |
| Suppression RuleやArchive運用はあるか | 未対応Findingの見え方に影響するため |
| Findingエクスポート先S3や長期保存先はあるか | A4の証跡保存と関係するため |

### 6.3 運用チーム向け

| 確認事項 | 理由 |
| :--- | :--- |
| アラートを最初に見る担当は誰か | 一次対応者を明確にするため |
| 確認頻度は日次、営業日、月次、随時のどれか | A4の証跡頻度を決めるため |
| 夜間休日の対応はあるか | 手順書の対象時間帯を決めるため |
| 対応記録はどこに保存しているか | 証跡テンプレートの保存先を決めるため |
| 月次確認資料はA4の証跡として利用できるか | 新規運用を増やすか判断するため |
| 対応完了の判断者は誰か | 終了条件を明確にするため |

### 6.4 セキュリティ担当部署向け

| 確認事項 | 理由 |
| :--- | :--- |
| Severityごとの対応基準はあるか | High、Medium、Lowの扱いを統一するため |
| 誤検知、対応不要、Archiveの判断基準はあるか | Findingを個人判断で処理しないため |
| エスカレーション基準はあるか | 重大アラート時の連絡漏れを防ぐため |
| 報告書やインシデント票の様式はあるか | 手順書と証跡様式を既存ルールに合わせるため |
| 監査提出時に必要な証跡粒度はどこまでか | A4の証跡不足を再発させないため |

### 6.5 アプリ/業務チーム向け

| 確認事項 | 理由 |
| :--- | :--- |
| 対象リソースの業務用途を誰に確認するか | Finding対象が正当な業務通信か判断するため |
| 予定作業や変更管理との突合先はどこか | 正常作業と不審操作を切り分けるため |
| 業務影響ありの場合の連絡先はどこか | 障害・インシデント対応へつなげるため |
| アプリ側ログや業務ログの確認先はどこか | AWSログだけで判断できない場合に備えるため |

## 8. 作業順序案

| 順序 | 作業 | 完了条件 |
| :--- | :--- | :--- |
| 1 | 既存資料を確認する | 必要資料の有無、所在、最新版が整理されている |
| 2 | GuardDutyと通知経路の現状を確認する | Detector、Finding、EventBridge、SNS、Teams/メール、Security Hubの現状が整理されている |
| 3 | 関係部署へヒアリングする | 一次対応者、判断者、通知先、証跡保存先、レビュー先が整理されている |
| 4 | ギャップを整理する | 手順不足、証跡不足、通知不明、対象範囲不明が一覧化されている |
| 5 | 運用設計を固める | 異常判定、エスカレーション、証跡保存、完了条件が決まっている |
| 6 | 手順書と証跡テンプレートを作成する | A3手順書、A4証跡テンプレートがドラフト化されている |
| 7 | 机上確認または運用試験を行う | サンプルまたは既存アラートで記録できることを確認している |
| 8 | レビューを受ける | 指摘事項が反映されている |

## 9. スコープ外または要確認

| 項目 | 扱い |
| :--- | :--- |
| GuardDutyの新規有効化 | 正式資料や現場方針で必要と判断された場合のみ別作業として扱う |
| GuardDuty Protection Planの追加有効化 | 料金、対象サービス、運用影響があるため、A3/A4手順書作成とは分けて確認する |
| EventBridge通知の新規作成 | 既存通知経路がない場合に検討する。4番台通知設定との重複に注意する |
| 自動隔離や自動修復 | 手順書作成とは別の設計・承認が必要 |
| 本番でのSample Finding作成 | 事前承認が必要。不可の場合は既存Findingまたは机上確認で代替する |

## 10. リーダーへ確認する文面案

```text
A3/A4について、手順書作成前に必要な作業を整理中。

現時点では、A3はGuardDuty等のセキュリティアラート確認・判断・エスカレーション・記録手順の作成、A4はその手順に沿った確認記録・調査証跡テンプレートの整備として進める想定。

手順書に実運用を反映するため、以下を確認したい。

・既存のセキュリティアラート運用手順、月次確認資料、インシデント対応手順の所在
・GuardDuty通知を最初に受ける担当、一次対応者、判断者、エスカレーション先
・FindingのSeverityやArchive、対応不要、誤検知の判断基準
・A4の証跡として残すべき粒度、保存先、レビュー先
・Sample Findingまたは既存Findingを使った机上確認/運用試験の可否
```
