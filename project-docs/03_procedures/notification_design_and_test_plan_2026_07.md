# 通知設計・通知先一覧・通知テスト手順

作成日: 2026-07-12

この資料は、クラウドセキュリティ対応で追加・変更する通知設定について、通知先、通知経路、テスト方法、確認事項を整理するための資料である。

正式な評価シートでは、4番台の監視項目について「検知時にアラートが発報されるよう構成すること」が推奨されている。通知設定は、CloudWatch Alarm、SNS、メール、Teams、EventBridge、既存監視基盤が関係するため、作業前に整理する。

## 1. 目的

- 通知先の誤設定を防ぐ
- メールやTeamsへの重複通知を防ぐ
- 既存通知経路と新規通知経路を整理する
- 通知テストの承認範囲を明確にする
- 本番反映時の通知影響を抑える

## 2. 通知経路の候補

| 経路 | 概要 | 確認事項 |
| :--- | :--- | :--- |
| CloudWatch Alarm -> SNS -> メール | 標準的なメール通知 | SubscriptionがConfirm済みか |
| CloudWatch Alarm -> SNS -> Teams | Chatbot、Webhook、Lambdaなどを経由 | 方式、管理者、投稿先Channel |
| EventBridge -> SNS | イベントを直接SNSへ送る | CloudWatch Alarmと重複しないか |
| EventBridge -> 別アカウントEvent Bus | 監視集約アカウントへ送る | 送信先、受信側Rule、運用主体 |
| EventBridge -> Lambda | 通知加工または自動対応 | Lambdaの処理内容と影響 |
| GuardDuty -> EventBridge -> 通知 | Finding通知 | Sample Finding投入時の影響 |

## 4. SNS Topic確認項目

| 項目 | 確認内容 |
| :--- | :--- |
| Topic名 | 現場命名規則に合っているか |
| Topic ARN | Alarm Actionに指定する値 |
| 暗号化 | KMS暗号化有無 |
| Access Policy | CloudWatchやEventBridgeからPublish可能か |
| Subscription | メール、Lambda、HTTPS、Chatbotなど |
| Subscription状態 | Confirmedか |
| 所有者 | 管理チーム |
| 利用中Alarm | 他用途で使われていないか |

## 5. Teams通知確認項目

Teams通知は複数方式があり得る。

| 方式 | 確認内容 |
| :--- | :--- |
| AWS Chatbot | Chatbot設定、SNS Topic、Teams Channel、IAM Role |
| Webhook | Webhook URLの管理者、秘匿方法、送信元 |
| Lambda連携 | Lambdaの処理内容、環境変数、送信先 |
| EventBridge API Destination | Connection、認証、送信先URL |
| 監視基盤連携 | 監視製品側の受信設定 |

Teams通知の確認事項:

- 投稿先Team / Channel
- 通知を受ける運用チーム
- 通知文面
- 本番テスト投稿可否
- 夜間・休日通知の扱い
- 誤通知時の連絡先

## 6. 通知テスト方針

通知テストは、以下の順に安全側から行う。

| 段階 | 方法 | 実通知 | 用途 |
| :--- | :--- | :--- | :--- |
| 1 | Metric Filter Patternテスト | なし | 検知条件の確認 |
| 2 | CloudWatch Alarm設定確認 | なし | Action設定の確認 |
| 3 | SNSテスト通知 | あり | 宛先到達確認 |
| 4 | 承認済み疑似イベント | あり | 監視経路全体の確認 |
| 5 | 本番相当テスト | あり | リリース判定 |

## 9. 通知設計で現場側へ確認すること

| No. | 質問 | 理由 |
| :--- | :--- | :--- |
| 1 | 既存のセキュリティ通知用SNS Topicはあるか | 新規作成を避け、既存運用に合わせるため |
| 2 | メール通知先は誰か | 通知先誤りを避けるため |
| 3 | Teams通知先Channelはどこか | 投稿先を確定するため |
| 4 | 通知テストを本番環境で実施してよいか | 誤通知扱いを避けるため |
| 5 | EventBridgeで別アカウント送信している通知は正式運用か | 監視重複を判断するため |
| 6 | 通知先の追加・変更に申請が必要か | 変更管理に従うため |
| 7 | アラート受信後の一次対応者は誰か | A3/A4の運用手順と合わせるため |
| 8 | 通知文面に含めてよい情報は何か | アカウントIDやリソース名の扱いを確認するため |

## 10. 完了条件

| 条件 | 内容 |
| :--- | :--- |
| 通知経路確定 | CloudWatch Alarm / EventBridge / SNS / Teamsの経路が明確 |
| 通知先確定 | メール、Teams、運用担当が明確 |
| テスト承認 | 通知テスト可否と日時が確定 |
| テスト完了 | 到達確認が完了 |
| 証跡保存 | 通知画面、メール、Teams投稿、Alarm履歴が保存済み |
